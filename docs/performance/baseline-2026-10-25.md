# Performance baseline: 25 October 2026

The state of the site before any performance work, so later runs can be compared against it.

- **Commit measured:** `f1f5759` (main, after PR #28 "footer-star")
- **Build:** production (`pnpm --filter @lootledger/web build`, then `vite preview`), with the local API on :3001 behind the preview proxy
- **Machine:** Windows 11, Intel Iris Xe (integrated GPU), Chrome stable, 1440×900 window for desktop runs
- **Data:** 4,179 items from 9 stores (library built 2026-10-24)
- **Runs:** one per configuration unless noted. Expect run-to-run noise of about ±5 percentage points on the dropped-frame figures.

## Summary

| Area | Result | Verdict |
|---|---|---|
| Lighthouse, desktop | Performance 98–99 | Good |
| Lighthouse, mobile | Performance 63–64 (LCP 4.0 s, TBT 640–890 ms) | Needs work |
| Grid scroll, desktop | ~30% of frames over budget, plus a ~0.9 s freeze when the 3D controller loads | Visible jitter |
| Game dialog open, desktop | 21–31 slow frames per open; typical frame 33 ms (30 fps) | Visible jank |
| Game dialog close, desktop | First frame frozen 100–250 ms | Visible hitch |
| Whole-page scroll, mobile-class | 9 fps average, 5.8 fps in the grid | Poor |
| Idle (no input), mobile-class | Main thread 81–89% busy | Poor |

Findings:

- **Nothing is drawn before the JavaScript runs.** `index.html` ships an empty `#root`, so first paint waits for React. The 15 KB (gzipped) stylesheet also blocks rendering, an estimated 300 ms on mobile.
- **On the home page the LCP element is the loading screen's "START" label.** Of the 4.0 s, 22 ms is the server response and 3.9 s is render delay.
- **Total Blocking Time comes from a few long tasks:**
  - React's first render: 504 ms (mobile)
  - Rendering data as it arrives: 306 ms on home, 492 ms on /deals (in the `query` chunk)
- **Home does about 3× the main-thread work of /deals** (14.0 s against 4.8 s, of which 6.5 s is "Other"). The likely cause is the always-running animations (section 4).
- **Unused JavaScript is about 48–54 KB.** Most of it is in the `api` chunk, which actually holds lucide and UI-library code.
- **Accessibility:** /deals has an element with a prohibited ARIA attribute.
- **SEO:** `robots.txt` is reported invalid because preview serves `index.html` for it. Check production.

## 2. Grid scroll (desktop)

**Method.** The script starts with the top of the grid at the top of the screen, rests the pointer in the middle of the viewport (over the cards, as a real user's would be) and sends 40 mouse-wheel notches of 120 px. Notches come 90 ms apart, with a 600 ms pause after every fourth. The wheel goes through Lenis.

**Metrics.**
- "Frames over budget": moving frames longer than 20 ms.
- "Scroll-step jumps": frames whose scroll step is more than 1.6× its neighbours'. This is the visible jitter, where Lenis catches up after a slow frame.

| Configuration | Frames over budget | p95 frame | Worst frame | Scroll-step jumps | Style recalc | Layout |
|---|---|---|---|---|---|---|
| As shipped | 27–29% | 50 ms | **917–967 ms** | 24–28 | 1.9–2.2 s | 220–270 ms |
| 3D controller blocked | 28–33% | 50 ms | 117–133 ms | 19–32 | 1.9 s | 240–280 ms |
| …and card hover disabled | 16–22% | 33 ms | 50 ms | 21–26 | 0.95 s | 85–93 ms |
| …and cover images hidden | 10% | 33 ms | 50 ms | 19 | 0.95 s | 38 ms |
| 3D blocked, header blur and grain off | 29% | 50 ms | 117 ms | 28 | 1.9 s | 252 ms |
| 3D blocked, card clip-path reveal off | 28% | 50 ms | 118 ms | 32 | 2.4 s | 209 ms |
| 3D blocked, no hover, `scrolling-fast` class never toggled | 16% | 33 ms | 50 ms | 18 | 0.87 s | 84 ms |

Causes, biggest first:

1. **The footer's 3D controller loads mid-grid.**
   - `footer-controller.tsx` starts the load once the footer is within 150% of the viewport. With the first page of games, that point is inside the grid.
   - Decoding the cube-map PNGs and the model then takes 850–970 ms in a single frame.
2. **Card hover effects start on cards passing under a resting pointer.**
   - The `scrolling-fast` guard only applies above 4 px per frame, and every Lenis glide ends below that. Result: 22–27 card hovers per run.
   - Each hover starts:
     - a `grid-template-rows` transition (a layout pass every frame for 500 ms)
     - a 40 px glow `box-shadow` transition (repainted every frame)
     - the tilt springs, the blended glare and the colour transitions
     - a hover sound
3. **Store images are 2–4× larger than they're drawn.** Cards are drawn 276 px wide.

   | Image source | Natural width | Decoded size |
   |---|---|---|
   | Venture Games | 800 px | 2.6 MB avg |
   | GamePark | 1000 px | 4.0 MB |
   | Pak Game Shop | 600 px | 1.8 MB avg |
   | Sky Games | 600 px | 1.4 MB avg |
   | Shopify (resized by its CDN) | 288 px | 0.4 MB |

4. **Baseline per-frame cost.**
   - TanStack Virtual renders new rows synchronously in the scroll event (`flushSync`).
   - The infinite CSS animations keep a style recalculation running on almost every frame (section 4).

**Not measurable contributors:** header `backdrop-filter`, the grain overlay, the `clip-path` card reveal, and the `scrolling-fast` class toggling.

## 3. Game dialog open and close (desktop)

**Method.**
- With the grid in view, click a fully visible card, wait 1.6 s, press Escape, wait 1.2 s.
- Done for two uncached games, then the first game again (cached).
- Recorded every frame: frame time, page width, and the flying panel's box.

| Configuration | Open: slow frames (>20 ms) | Open: typical frame | Open: worst frame | Close: slow frames | Close: worst frame |
|---|---|---|---|---|---|
| As shipped | 21–31 | 17–34 ms | 167–233 ms | 7–8 | 117–200 ms |
| Backdrop blurs off | 8–12 | 16.7 ms | 183–234 ms | 5–10 | 166–184 ms |

What each open and close does to the page:

| Measurement | Open | Close |
|---|---|---|
| Blocked time before the animation starts | 73–233 ms (click handler; includes 59–103 ms forced layout) | 67–89 ms (`popstate` render; ~30 ms forced layout) |
| Page width | 1426 → 1440 px (scrollbar removed) | 1440 → 1426 px (scrollbar restored) |
| Layout passes | 41–68 | 52–57 |
| Style recalcs | 131–187 | 96–118 |

A DevTools trace of one open plus close (3 s) shows:
- GPU main thread busy 1.4 s, of which 1.37 s is raster work
- 134 main-thread frames in 3 s, about 45 fps

Causes:

1. **Backdrop blurs.** The overlay applies `backdrop-blur-[8px]` across the whole page while fading in. The dialog content has `backdrop-blur-[37.5px]`. The panel flies over both, so the page is re-blurred every frame.
2. **The flying panel animates layout properties.** It animates `top`, `left`, `width` and `height`, not `transform`, so layout runs and the panel and its image are redrawn every frame.
3. **Synchronous render on the first frame.** The animation clock keeps running during that render, so the panel's first visible step jumps (up to 234 px of width in one frame). Cached games are the worst case because the whole dialog body renders in the click.
4. **The scrollbar is removed and restored.**
   - `lenis.stop()` sets `overflow: clip` on `<html>`, so the whole page relayouts and the virtual grid resizes every card behind the overlay.
   - On close, the target card is measured before the scrollbar returns. The panel therefore lands up to ~11 px off (right-hand column) and snaps.
5. **The panel retargets mid-flight, and the dialog remounts on landing (likely; not isolated).**
   - The panel flies to the dialog's live box, which grows when the offers arrive.
   - On landing, the dialog body is remounted (`key` changes from "measuring" to "shown"), so it renders and restarts its entrance animations in that same frame.

## 4. Whole-page scroll and idle

**Method.**
- Dismiss the intro.
- Measure 3 s idle at the top.
- Scroll top to bottom in 120 px wheel notches every 50 ms, through Lenis, with the pointer parked at the edge.
- Measure 3 s idle at the bottom.
- Scroll back up fast.

**Profiles.**
- **Desktop:** 1440×900 at 1×.
- **Mobile-class:** 390×844 at 3× pixel density with 4× CPU slowdown. The GPU is not slowed, so real phones may do worse.

Mobile figures come from a run without tracing; tracing adds overhead under CPU throttling.

| Section | Desktop fps (dropped) | Mobile-class fps (dropped) |
|---|---|---|
| Idle at top | 60 (0%), main thread 16–23% busy | 50–55 (9–17%), **main thread 81–89% busy** |
| Hero | ~38 (36%; small sample at scroll start) | 13 (66%) |
| Grid | 51 (15.5%) | **5.8 (65%)**, typical frame 167 ms |
| Grid into footer | one 115 ms hitch | 11, plus one 2.4 s freeze (3D model parse) |
| Footer (3D controller) | 59 (1.3%) | 26 (56%) |
| Fast scroll up | 56 (7%) | 7 (88%) |

Desktop scroll trace (13.8 s):

| Measure | Value |
|---|---|
| GPU raster | 2.8 s |
| Render passes | 4,069 (about 5 per frame) |
| `Layerize` time | 1.1 s (1.5 ms per frame) |
| Compositor layers | 26 at the top, 27 in the grid, 18 at the footer |
| Elements with `will-change` | 11 |

Main-thread cost while idle (mobile-class, style recalc per 3 s):

| Infinite animations disabled | Main thread busy | Style recalc |
|---|---|---|
| None (as shipped) | 81% | 426 ms (194×) |
| Hazard band only | 71% | 470 ms |
| Grain only | 77% | 450 ms |
| Equalizer only | 73% | 347 ms |
| Hazard band and equalizer | 51% | 266 ms |
| Hazard band, equalizer and grain | 50% | 63 ms (37×) |

Any one of these animations keeps the per-frame style recalc going.
- `hazard-slide` animates `background-position`, which can't be composited, and runs even while off-screen.
- The remaining idle cost is script. Lenis's frame loop is registered with keep-alive (`smooth-scroll.tsx`), so it runs every frame forever.

Other scroll-time costs:

- **Hero:**
  - The title animates `filter: blur()` with scroll.
  - The pointer glow is `blur(120px)` on a 42vw element.
  - The header's `backdrop-filter: blur(16px)` re-blurs whatever scrolls under it.
  - The grain is a fixed layer covering the full screen plus 10% overscan.
- **Grid on mobile-class:** the virtualizer's scroll handler took about 12 s of a 100 s run (synchronous row renders).

## How to compare after changes

Re-run the same measurements on the same machine and write a new report next to this one. The scripts used for this report are in [`bench/`](bench/).

| Script | Measures |
|---|---|
| `scroll-bench.cjs <desktop\|mobile> <outdir>` | whole-page scroll and idle (`NOTRACE=1` for mobile) |
| `grid-bench.cjs center` | grid scroll; `BLOCK3D=1`, `CSS=…` and `JS=…` for A/B tests |
| `dialog-bench.cjs` | dialog open and close; `CSS=…` for A/B, `TRACE=1` to save a trace |
| `analyze.cjs <scroll-*.json>` | summarizes `scroll-bench` output by page section |
| `trace.cjs <trace.json>` | totals a trace's time by thread and event |
| Lighthouse | `npx lighthouse <url> --output=json --chrome-flags=--headless=new`, with and without `--preset=desktop` |

To run them:

1. Build and serve the site: `pnpm --filter @lootledger/web build`, then `pnpm --filter @lootledger/web preview`, with the API on :3001.
2. Install `puppeteer-core` in a folder outside the repo (`npm i puppeteer-core@24`). Run the scripts from that folder, with `NODE_PATH` pointing at its `node_modules`, e.g. `NODE_PATH=./node_modules node <repo>/docs/performance/bench/grid-bench.cjs center`. Output files are written to the current folder.

The scripts launch headed Chrome from its default Windows path, so they use the real GPU.
